# Megolm: Group Ratchet(群组棘轮加密)

> 原文:https://spec.matrix.org/v1.19/olm-megolm/megolm/
> 规范版本:v1.19 · 类型:加密协议

## 一句话概述

Megolm 是一个**基于 AES 的密码学 ratchet,面向群组通信**设计——在群聊中,像 Olm 那样的点对点(peer-to-peer)系统对每条消息逐个设备加密不切实际,Megolm 用"一次加密、多设备共享"的方式加密房间消息本体。规范文档采用 Apache License, Version 2.0 授权。

## 密码学原语

以规范原文为准,本页明确出现的原语如下:

| 原语 | 用途 |
| --- | --- |
| **AES-256-CBC + PKCS#7 padding** | 加密算法 |
| **HMAC-SHA-256 截断为 64 位(8 字节)** | 消息 MAC(取 HMAC-SHA-256 的前 8 字节) |
| **Ed25519 密钥对** | 签名(64 字节签名),对出站会话进行认证 |
| **SHA-256(作为 HKDF 的哈希)** | 即 HKDF-SHA-256,用于派生 AES/HMAC 子密钥 |
| **HMAC-SHA-256(单字节 key `\x00`/`\x01`/`\x02`/`\x03`)** | ratchet 的推进哈希函数 H0–H3 |

注意:**Curve25519 与 SHA-512 在本页并未出现**。Megolm 不像 Olm 那样用 Diffie-Hellman,而是用"共享 ratchet 状态 + Ed25519 签名"的模型。

## 工作原理

### 出站会话(Outbound Session)

一个出站会话由三部分组成:

- 一个 **32 位计数器 i**(counter,初始为 0);
- 一个 **Ed25519 密钥对 K**(新生成);
- 一个 **ratchet R_i**,由四个 256 位值组成(共 1024 位,初始取自 1024 位随机数据)。

### 入站会话(Inbound Session)

接收方用会话的 Ed25519 公钥校验签名后,存储计数器、ratchet 与公钥。入站会话应保留其**已知最早的 ratchet 值**以维持解密能力,但"可以选择缓存已计算过的 ratchet 值"。

### Ratchet 前进(Ratchet Advancement)

ratchet R_i 由四个 256 位部分 R_{i,0}、R_{i,1}、R_{i,2}、R_{i,3} 组成,按不同间隔推进:

- 每 **2^8** 次迭代,R_{i,3} 从 R_{i,2} 重新播种;
- 每 **2^16** 次迭代,R_{i,2} 与 R_{i,3} 从 R_{i,1} 重新播种;
- 每 **2^24** 次迭代,R_{i,1}、R_{i,2}、R_{i,3} 从 R_{i,0} 重新播种。

推进所用的哈希函数定义为 HMAC-SHA-256、以单字节为 key:

```
H0(A) = HMAC(A, "\x00")
H1(A) = HMAC(A, "\x01")
H2(A) = HMAC(A, "\x02")
H3(A) = HMAC(A, "\x03")
```

该设计允许把 ratchet 任意向前推进,而"最多只需 1020 次哈希计算"。

### 密钥派生与加密

用 HKDF(空 salt、ratchet 作为 IKM、info 字符串 `"MEGOLM_KEYS"`、输出 80 字节)派生三个子密钥:

```
AES_KEY_i ∥ HMAC_KEY_i ∥ AES_IV_i = HKDF(0, R_i, "MEGOLM_KEYS", 80)
```

即 256 位 AES 密钥、256 位 HMAC 密钥、128 位 AES IV。明文用 AES-256-CBC 加密得到密文 X_i。随后对整条消息做 HMAC-SHA-256,取前 8 字节作为 MAC;MAC 之后,再用 Ed25519 密钥对整条已认证消息签名。

### 消息序号(Message Index)

ratchet 下标 i 是一个 **32 位大端整数**(在会话共享格式中如此表示);在消息 payload 中则用 **Protocol Buffers 的变长整数编码**。消息 payload 使用两个 tag:

- `0x08` Message-Index(integer 类型):即 ratchet 下标 i;
- `0x12` Cipher-Text(string 类型):即密文 X_i。

### 消息格式

Megolm 消息由:版本字节 `"\x03"` + 变长 payload + 8 字节 MAC + 64 字节签名组成。

- MAC 覆盖其前所有字节;
- 签名覆盖其前所有字节。

### 会话共享与导出

- **会话共享格式(version `"\x02"`)**:共 229 字节,包含版本(1)、ratchet 下标 i(4,大端 32 位)、四个 ratchet 值 R(i,0)–R(i,3)(各 32)、Ed25519 公钥 K_pub(32)、签名(64)。对"直到 K_pub 为止"的数据用 Ed25519 密钥对签名后追加 64 字节签名。共享时把会话状态(ratchet + 公钥 + 签名)分发给其他设备,用于加入群聊。
- **会话导出格式(version `"\x01"`)**:共 165 字节,与共享格式相同但**去掉签名**。原因:ratchet 下标 i 被签名覆盖,转发/推进 ratchet 会改变 i,从而令签名失效,因此导出格式不再携带签名。

### 会话轮换(Session Rotation)

由于 Megolm **缺少后向保密(backward secrecy)**,规范指出:"应用应确保 Megolm 会话不被无限期使用",应定期启动新会话,并通过安全通道(即 Olm)共享新密钥。成员退群后也必须轮换会话,否则退出的成员仍可继续解密后续消息。

## 在 Matrix 中的角色

> 说明:Megolm 规范页本身聚焦 ratchet 算法。以下"加密房间消息本体"的角色来自 Matrix 端到端加密总体设计(索引页只有一句:"Matrix uses the Olm and Megolm cryptographic ratchets for end-to-end encryption")。

- **加密房间消息本体**:房间内每条消息由 Megolm 出站会话加密一次,同一房间的多个接收设备共享同一把会话密钥(通过会话共享格式 + Olm 点对点分发),而不是逐设备加密。
- **与 Olm 分工**:Olm 负责设备间安全地把 Megolm 会话密钥(room key)送到每个接收设备;Megolm 负责用这把密钥加密房间里的实际消息。二者是"密钥分发"与"消息加密"的分层关系。

## 安全性质与已知限制

- **仅部分前向保密(partial forward secrecy)**:一旦某个 ratchet 值 R_i 泄露,攻击者就能解密由该值及之后各值派生的所有消息密钥。缓解办法:把已存储的 ratchet 值向前"滚动"(wind forward),或干脆丢弃该会话。
- **无后向保密(no backward secrecy)**:拿到会话状态的一方可以向前解密后续消息,因此必须定期轮换会话、成员退群后轮换。
- **重放(replay)**:同一消息可被多次解密,应用应跟踪并拒绝已见过的 ratchet 下标。
- **无转录一致性(no transcript consistency)**:不同接收方可能收到不同的消息集合(被恶意或故障节点选择性投递时),Megolm 本身不保证全体成员看到完全一致的历史。
- **依赖安全通道**:若点对点(Olm)通道存在未知密钥共享或重放等漏洞,这些漏洞会延伸到 Megolm 会话。

## 易混淆点 / 笔记

- **Megolm 的"群组"不是群签名**:Megolm 用"一个 Ed25519 密钥对 + 共享 ratchet",签名只认证"消息来自某个持有该会话密钥的人",并不区分具体是哪位成员——它不像群签名那样提供成员身份可追责性。
- **ratchet 推进的间隔方向**:是"低频值从高频值重新播种"(2^8 → 更新 R_{i,3},2^16 → 更新 R_{i,2}、R_{i,3},2^24 → 更新 R_{i,1}、R_{i,2}、R_{i,3})。R_{i,0} 逐消息推进,是最高频的基础。
- **1020 次哈希**是"任意大步前进"的上界,正常逐消息前进每步只需极少次 HMAC,开销极低。
- **共享格式(0x02)带签名、导出格式(0x01)不带**:导出会丢签名是因为 i 被签名覆盖、ratchet 推进后签名失效;别把两者当成同一物。
- **前向 vs 后向**:前向保密 = 泄露当前状态不能回溯解密历史(仅部分满足,取决于 ratchet 是否已滚动);后向保密 = 泄露当前状态不能解密未来(不满足)。Megolm 的软肋是后者。
- **重放防护不在密码学层**:Megolm 的 MAC+签名不能阻止重放,防重放要靠应用层记录已处理的 ratchet 下标。

## 与自托管聊天项目(Babacom)的相关性(25 人小群、跨境,是否值得开 E2EE、开销)

- **是否值得开**:值得,且 Megolm 正是为"小群"这种场景设计的。跨境自托管下,消息明文经过服务器与网络路径,Megolm 让内容对服务器不可见;25 人小群一次加密即可覆盖全部成员,比 Olm 逐设备加密高效得多。
- **每消息固定开销(可量化)**:每条 Megolm 消息额外携带 8 字节 MAC + 64 字节 Ed25519 签名,加上 1 字节版本与 protobuf 编码的 Message-Index/Cipher-Text 标签,约 **70+ 字节的固定密文开销**;密钥派生是每消息 1 次 HKDF + 少量 HMAC,CPU 开销可忽略。对文字聊天而言几乎无感。
- **真正的成本在工程侧,不在性能侧**:需要维护会话轮换(成员退群、定期轮换)、设备列表与设备验证、密钥备份、以及防重放的下标跟踪。若 Babacom 直接复用 Matrix 生态(Synapse/Dendrite + 官方 SDK),这些由 SDK/服务端承担;若自研协议,则需自行实现会话共享格式与轮换逻辑。
- **退群必须轮换**:25 人小群里成员变动较频繁,必须把"成员退群 → 立即轮换 Megolm 会话并用 Olm 重新分发新密钥"作为硬性流程,否则退群者仍可解密后续消息(无后向保密)。
- **结论**:对跨境小群,开启 E2EE 的隐私收益明显、性能开销可忽略;成本主要在密钥管理复杂度,建议优先复用成熟 Matrix 客户端实现而非自研。
